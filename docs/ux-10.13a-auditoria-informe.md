## Recorridos y estados observados

### Navegación principal

Se recorrió Dashboard → Trabajos → expediente → tribunal, y expediente → evaluación → resultado → Documentos/PDF. También se comprobó Cronograma → expediente, y las rutas de seguimiento y catálogos. La navegación lateral distingue Maestros, Operación, Gestión académica y Seguimiento; la página activa tiene tratamiento visual. El contenedor común ofrece migas de pan, vínculo para saltar al contenido, botón de colapsar la barra y menú nativo `<details>` en ancho reducido.

La pantalla de alta de trabajo API dice expresamente que el expediente y sus relaciones proceden de otro sistema. La asignación institucional del tribunal también se presenta como lectura. Esas ausencias son límites de integración acordes al alcance y **no** se califican como defectos.

### Evaluaciones y resultados

La lista entrega el trabajo y sus estudiantes. En el editor observado, el selector «Miembro del tribunal» enumeró los dos integrantes confirmados y la pantalla indicó que el servidor valida su pertenencia. No es un selector de cuenta. El selector de etapa incluyó `TRABAJO_COMPARTIDO` y `ESTUDIANTE_INDIVIDUAL`; para la etapa compartida mostró que existe un único registro y permitió elegir estudiante para el PDF. El expediente sintético tenía evaluaciones cerradas, así que no se probaron Guardar, Cerrar, errores de campos ni conflictos concurrentes.

La consolidación del servidor quedó visible en resultado individual: etapa escrita compartida 9.30, etapa oral individual 8.70 y promedio final 9.00/10. La página marca la consolidación como consultiva y ofrece PDF por miembro. Esto no reproduce el antiguo F-01: la respuesta se adaptó y cargó; una solicitud anterior abortada al cambiar de ruta fue seguida por GET 200. No se hizo escritura.

### Estados, formularios y documentos

- **Carga:** los módulos muestran estado de consulta mientras esperan la API. Una carga inicial se observó en Resultado, Documentos y el editor de rúbrica; después de completar los GET aparecieron los datos.
- **Ausencia:** las actas archivadas mostraron 0 y el texto de consulta correcta. No se confundió ese estado con error.
- **Error/reintento:** las rutas y componentes contienen avisos de error/reintento. No se provocó indisponibilidad de NestJS para no desconectar el entorno ni alterar la fuente.
- **Evaluación:** 10.9B solo contenía evaluaciones cerradas en los trabajos revisados. Los estados abiertos/incompletos/legacy no se observaron visualmente; su tratamiento permanece documentado y cubierto por código/pruebas de etapas anteriores.
- **Documento preliminar/acta:** el texto del módulo distingue nota mínima provisional, vista previa sin número, generación/reimpresión y archivo. No se emitió acta ni se abrió una vista preliminar.
- **Formulario de rúbrica:** se inspeccionaron los campos, ponderaciones, etapas y botones. El guardado no se pulsó.
- **Cronograma y catálogos:** se observaron las acciones disponibles, pero no se abrieron operaciones de escritura ni se enviaron formularios.

El PDF de rúbrica se recuperó desde `GET /api/v1/documentos/trabajos/:trabajo/estudiantes/:estudiante/rubricas/:miembro/pdf`, respuesta 200. En móvil se mostró en un `iframe` de aproximadamente 309 px de ancho por 780 px de alto, con barra del lector para guardar o imprimir. ## Navegación, jerarquía y componentes

### Puntos que funcionan bien

- El menú agrupa catálogos, operación, gestión académica y seguimiento; resalta la página actual.
- Las migas de pan y los enlaces de retorno contextualizan el expediente, la etapa y el documento.
- Los expedientes API enlazan con UUID entregados por el servidor.
- Los avisos de origen distinguen consulta API; las vistas de seguimiento indican que no usan prototipo como fallback.
- Las etiquetas de estados incluyen texto además de color. Resultados separados por estudiante conservan la procedencia de la etapa compartida.
- `TablaCatalogo` dispone de caption, sort accesible, etiquetas de columnas, búsqueda y wrapper enfocable. Los formularios revisados asocian etiquetas con controles.
- La plantilla común incluye enlace «Saltar al contenido principal», `<main>` identificado, navegación con `aria-label` y foco visible en controles clave.

### Diferencias a normalizar

- Conviven `TablaCatalogo`, tablas responsivas de seguimiento y tablas particulares de Cronograma/rúbricas. Cambian el desplazamiento, comportamiento en móvil, controles de orden y envoltura de acciones.
- Los avisos API usan paneles informativos; otras acciones usan SweetAlert2 y el resguardo de formulario conserva `window.confirm`.
- Hay varios estilos específicos por pantalla junto con `aplicacion.css`, un archivo global extenso. No es un fallo visual por sí mismo, pero aumenta el riesgo de divergencia al ajustar breakpoints.
- Los formularios de configuración abarcan varios grupos; la creación de rúbrica acumula configuración general, carreras, etapas, categorías, indicadores y resumen. Mantener el resumen final y el acceso a errores cerca de la acción de guardar facilitará la revisión.

## Propuesta de diseño para GENARES

1. **Navegación centrada en tareas:** mantener el menú actual por áreas y proporcionar una ruta visible Expediente → Tribunal confirmado → Agenda → Evaluaciones → Resultado → Documentos. Catálogos permanecen como configuración de apoyo. Sin asociar áreas a nuevos roles técnicos.
2. **Proveniencia inequívoca:** cada pantalla debe tener una sola fuente operativa visible. Ocultar elementos locales en modo API; en prototipo, marcar «Datos de demostración» de forma persistente. No usar un mensaje local para representar actividad académica real.
3. **Jerarquía de expediente:** identificar primero código/título, carrera/período y estado; después estudiantes y tutoría; luego tribunal, agenda, versión de rúbrica y evaluación. Los vínculos primarios deben usar UUID del origen activo.
4. **Estados académicos uniformes:** usar etiqueta textual más color para abierta, cerrada, incompleta, resultado completo, preliminar y acta archivada. Separar estado del registro, capacidad de escribir y oficialidad del documento.
5. **Resultados:** mostrar una tarjeta por estudiante; listar etapas con ámbito explícito, promedio y origen de transferencia; rotular el resultado final como promedio sobre 10. Diferenciar expresamente resultado consultivo, umbral provisional y acta archivada.
